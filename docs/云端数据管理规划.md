# 云端数据内容管理规划

> 日期：2026-08-06（自动生成，供次日审阅）
> 范围：分析当前云端（远端服务器）数据能否被“管理”，以及要落地哪些管理能力。
> 结论先行：**能管理，但客户端目前只开放了“上传 / 查看 / 恢复 / 合并”，缺少“删除、清理、细看远端内容”的管理能力**；底层接口（Provider / 网关）已经具备删除等基础能力，主要是服务层与 UI 没接。

---

## 1. 现状盘点

### 1.1 云端到底存了什么

一个“仓库（repository）”里存的是按资料档（profile）组织的一套不可变快照 + 索引：

| 内容 | 说明 | 写入方 |
|---|---|---|
| Release（每个 tag 一个） | 每次备份生成一个 `data-v1-{profile}-{时间戳}-...` 的 Release | 客户端 `CloudBackupService.upload_backup` |
| snapshot.ebpack | Release 的资产（附件）：完整数据包（数据库/资源/元数据） | 同上 |
| 同步索引 manifest（latest.json） | 资料档快照指针、别名、设备、锁等 | 客户端写入，网关/本地文件夹存 |
| 写锁（lock） | 防多设备并发覆盖 | 客户端 acquire/release |

存储后端：
- **正式：腾讯云 CloudBase**（经仓库内 `cloudbase/gateway` 网关，RDB 存储）
- **离线测试：本地文件夹**（`LocalFolderProvider`，`backup_dir/cloud_local`）

### 1.2 现有能力矩阵

| 能力 | Provider 层 | CloudBackupService 层 | 客户端 UI |
|---|---|---|---|
| 列出远端备份 | `list_releases` ✅ | `list_backups` ✅ | ❌ 未接 UI |
| 查看云端资料/资料档 | `discover_profiles` / `profile_connection_state` ✅ | ✅ | ✅ 设置→查看云端资料 |
| 上传备份 | `create_release` + `upload_release_asset` ✅ | `upload_backup` ✅ | ✅ 手动/自动 |
| 下载/恢复 | `download_release_asset` ✅ | `download_backup` / `restore_profile_to` / `restore_latest_to` ✅ | ✅ 恢复 |
| 合并资料档 | — | `preview_profile_merge` / `merge_profile` ✅ | ✅ |
| **删除远端备份** | `delete_release` ✅（网关与本地文件夹都实现） | ❌ 无 `delete_backup` | ❌ |
| **清理旧备份/容量管理** | — | ❌ | ❌ |
| 查看远端包内容/元数据 | — | 仅 `list_backups` 有 tag/时间/大小等 | ❌ |
| 多资料档管理（重命名/归档/删除） | — | 仅别名（alias）写入 | ❌ |

> 关键点：**`CloudProvider.delete_release` 和网关的删除接口已经存在**（`CloudCapabilities.delete_release=True`），当前只在“上传失败后的清理”路径里用到，没有暴露成用户可用的“删除远端备份”。

### 1.3 当前数据流（简）

```
本地错题库/笔记 ── export_ebpack ──> snapshot.ebpack
        │
        └── upload_backup ──> CloudBase/本地文件夹：Release(tag) + manifest 索引 + 锁
        ▲
        └── 恢复/合并：download_backup → restore/merge → 写入独立目录
```

## 2. 目标：把“远端数据内容”做成可管理的

### 2.1 建议新增能力（按优先级）

**P0 —— 最基本、最常用**
1. **远端备份列表页**：列出仓库内所有备份（时间、资料档、大小、SHA、是否当前），支持刷新；复用现有 `list_backups`，补一个 UI（可放“设置 → 云端同步”或独立“云端数据”页）。
2. **删除单个远端备份**：服务层新增 `delete_backup(tag)`（调 `provider.delete_release` + 从 manifest 摘除该指针）；UI 删除前强制二次确认（“删除后不可恢复，不影响本地数据”）。
3. **删除“当前”备份保护**：若被删的 tag 是某资料档的当前快照，提示先恢复/确认，避免远端失去最新指针。

**P1 —— 体验与容量**
4. **清理策略**：按“保留最近 N 份 / 每资料档保留最近 M 份”清理旧快照；容量预警（网关有 `USER_STORAGE_BYTES` / `MAX_ASSETS_PER_RELEASE` 配额，客户端可读剩余空间提示）。
5. **远端内容预览**：把选中备份下载到临时目录，展示包内清单（题目/笔记数量、schema 版本、备份时间），不直接覆盖本地。

**P2 —— 进阶**
6. **多资料档管理**：资料档重命名（写别名）、归档、彻底删除远端资料档（连同其快照与索引，需强确认）。
7. **Web/独立管理端（可选）**：在 `cloudbase/gateway` 上加“管理”类只读/删除接口，供网页或脚本管理，客户端不感知。

### 2.2 涉及模块与改动点

| 模块 | 改动 |
|---|---|
| `cloud/base.py` | 能力标记已含 `delete_release`；可加 `list_remote_objects`（可选） |
| `cloud/cloudbase.py` / `local_folder.py` | 均已实现 `delete_release`，基本不动 |
| `cloudbase/gateway/index.js` | 已有删除/列出 action；如需管理端再补鉴权与批量接口 |
| `application/cloud_service.py` | 新增 `delete_backup(tag)`、`cleanup_backups(retain=N)`、`preview_backup(tag)`；删除后同步更新 manifest |
| `ui/main_window.py` / `settings_dialog.py` | 新增“云端数据”管理入口/列表/删除/清理 UI |
| 测试 | 为删除/清理/预览补单测（含本地文件夹与 CloudBase mock） |

### 2.3 安全与一致性

- **删除不可逆**：所有删除都走二次确认，并在文案中说明“只删云端快照，本地数据不受影响”。
- **多设备**：删除前检查锁与“是否被其他设备引用”；删除当前资料档快照需先恢复/确认。
- **索引一致性**：删除 Release 后必须同步从 manifest 摘除/标记，避免 `list_backups` 与索引不一致。
- **配额**：利用网关返回的配额字段做清理提示。
- **测试优先**：本地文件夹后端先全量验证，再上 CloudBase。

## 3. 落地步骤（建议）

1. 服务层：`delete_backup` + `cleanup_backups` + `preview_backup` + 单测（本地文件夹）。
2. UI：设置页新增“云端数据”区（列表 + 删除 + 清理按钮 + 确认弹窗）。
3. 联调 CloudBase 网关删除/清理，验证索引同步。
4. P1/P2 视验收情况再排期。
